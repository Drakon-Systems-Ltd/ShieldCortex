# #501 — OS-owned policy lock

*2026-09-16. Condensed from `shieldcortex-501-design-20260916.md`. Lands on
top of #500 (`1d57378d`, tool-call self-protection).*

## 1. What the config signature actually protects

Measured against `origin/main`, not remembered:

| Reader | Verifies `_sig`? | Effect of a same-UID edit |
|---|---|---|
| Claude Code hook (`loadActionGuardConfig`) | **No** — bare `JSON.parse`; also ignored `SHIELDCORTEX_CONFIG_DIR` | guard off, no forgery needed |
| OpenClaw plugin (`normaliseConfig` via the `openclaw.json` entry) | **No** — a different unsigned same-UID file | guard off, no forgery needed |
| `src/cloud/config.ts` `readRawConfigState` | Yes | `tampered` set `defenceMode: 'strict'` only; `actionGuard.enabled` was still read from the tampered bytes |
| doctor | Yes, indirectly | no tamper row existed |
| `hasTrustedMemorySidecarPosture` | Yes, strictly | the one place `_sig` gated a security decision — forgeable with the co-located key |

The conclusion that shaped everything below: the HMAC is a **corruption /
accidental-edit detector, not a tamper control**, and the two enforcement
surfaces never consulted it. Re-keying or relocating `.integrity-key` closes
nothing, because a same-UID process reads the key.

## 2. The shape

**Signing authority = the operating system's ownership boundary**, not a key the
agent can read.

- A human, once, as root, runs `shieldcortex protect`. It writes
  `/etc/shieldcortex/policy.json`, root-owned `0644`, in a root-owned `0755`
  directory. Agent-**readable** is fine and intended; agent-**writable** is the
  thing being removed. No cryptography: nothing to steal, no keyring, no second
  same-UID file.
- **Protected set v1** — `actionGuard.enabled`, `actionGuard.enforce`,
  `actionGuard.autoApprove` (ceiling), `actionGuard.broker.enabled`,
  `defenceMode` (floor), `memory.hostContract.posture`, `memory.inject.mode`.
- **Precedence** — for every covered key, take whichever of the lock and
  `config.json` is TIGHTER. That single rule is what "the lock wins; config may
  only tighten" means written as an operation rather than seven special cases.
  `autoApprove` is a ceiling (intersection); `defenceMode` is a floor (stricter
  rank); the two memory keys have no tightness order, so the lock is
  authoritative outright.
- **Verifier** — one function, one dist module: `lstat` says regular file and
  not a symlink, `uid !== euid`, no group/other write, and the same rules on
  every ancestor directory (unlink + create is governed by the DIRECTORY, not
  the file), then parses as JSON and matches the schema. Directories are checked
  with `stat` plus an `lstat` symlink-owner check, because `/etc` is a symlink on
  macOS and an lstat-only rule would refuse every Mac.

### Failing closed, precisely

- **Present but unverifiable** (wrong owner, writable dir, symlink, parse /
  schema fail, unknown version, dist verifier missing) → posture
  `{enabled: true, enforce: true, autoApprove: [], broker off, defenceMode: 'strict'}`,
  audit outcome `policy_unverifiable`, one stderr line. **Not** "deny every tool
  call": that bricks the agent and teaches operators to remove the lock.
- **Absent** → today's behaviour, plus a doctor row. FAIL when the guard is
  enabled (the operator believes tool calls are gated and a one-line edit says
  otherwise), WARN when it is off (nothing pinned to lose yet). Fix line is
  `protect`.
- **Agent running as root / Windows** → no lock is possible; doctor states it
  plainly. A remote policy authority is the later answer, not a fake local one.

### Schema versioning

Unknown KEYS are ignored, so a newer `protect` cannot push older installs on a
fleet into fail-closed. An unknown VERSION is a failure, because a v2 policy may
mean something a v1 reader would get quietly wrong.

## 3. Legacy local key — explicit compatibility

`.integrity-key`, embedded `_sig`, legacy `.config-sig` and the `self-heal`
verdict are **unchanged, not relocated, not migrated**. They keep their real job
(torn write / accidental edit) and the docs stop calling it tamper protection.

Two semantic fixes inside the existing scheme:

1. A `tampered` verdict now forces the whole fail-closed posture from §2, from
   the same constant. Previously it set `defenceMode` and nothing else, so the
   guard's own switches were read straight out of the bytes the integrity check
   had just called untrustworthy.
2. `hasTrustedMemorySidecarPosture` requires the lock to declare the posture when
   a lock exists, and falls back to `_sig` only when unlocked. A locked host
   whose lock is silent on the memory keys answers `false`: silence from the
   authority is not permission.

## 4. Both enforcement surfaces

One implementation of the precedence rules, in
`src/defence/iron-dome/policy-lock.ts`, imported from `dist` by both surfaces —
the hook through its existing lazy-dist pattern, the plugin through
`shieldcortex/defence`.

Behind each sits a small **inline existence probe** that imports nothing. A
missing dist normally degrades to the inline catastrophic fallback, because
turning every tool call into a denial whenever a build is stale is the outage
ShieldCortex exists to prevent — but on a host with a lock file that would make
"delete dist" the bypass. So a present lock plus an unavailable reader forces the
strict posture. Only the fail-closed literal is duplicated; the parity suite
asserts the two copies still match `STRICT_FAILCLOSED_POSTURE`.

Ordering matters on the plugin: the `openclaw.json` entry deep-merges OVER the
shield config, so the lock is applied AFTER `mergeConfigs`. Applied earlier, an
unsigned same-UID `enabled: false` would still have the last word — the exact
bypass being closed. `openclaw-plugin-guard-sync` writes into that same entry, so
it is out-ranked on read and refused on write.

The hook also now honours `SHIELDCORTEX_CONFIG_DIR`. It hard-coded
`~/.shieldcortex`, so on any box using the override it was enforcing against a
different config from the rest of the product.

## 5. The `SHIELDCORTEX_PROTECTED_ROOT` test seam

The design rule is "override only via a root-owned file, never env", and the
production override honours it: `/etc/shieldcortex.conf`, a root-owned pointer
file that must itself pass `verifyProtectedFile`.

`SHIELDCORTEX_PROTECTED_ROOT` is a separate, deliberately **non-loosening** test
seam. The canonical root is probed FIRST, and if anything exists there the
variable is ignored outright. An agent that sets it therefore cannot hide a real
lock; on a host with no lock the only thing it can do is introduce one, and a
lock the agent can write is by definition same-UID, hence unverifiable, hence
STRICTER than unlocked. It exists because the regression proof has to drive the
built dist and the built hook as separate processes and may not write to `/etc`.

## 6. Regression proof

`src/__tests__/policy-lock-dist-regression-501.test.ts` drives the BUILT
artefacts. Fixture: hermetic `HOME` + `SHIELDCORTEX_CONFIG_DIR`, a
`.integrity-key` and a `config.json` carrying a genuinely valid embedded `_sig`
computed with it (the SC-02 forge), `actionGuard.enabled: false` inside those
correctly-signed bytes, and a same-UID `policy.json`. The first assertion is that
the integrity check ACCEPTS the forgery — otherwise the suite would be proving
something weaker than it claims.

Then: `dist/index.js doctor --json` reports the lock invalid and the posture
enforced; the built `scripts/pre-tool-hook.mjs` DENIES the SC-01 catastrophic
payload; `config --action-guard-disable` is refused by name; `config
--cloud-status` prints the enforced posture (the assertion that travels through
`readRawConfigState`'s precedence rather than a surface that reads the lock
directly). The suite rebuilds on a STALE dist, not just a missing one: a build
left over from before the fix exists, and would report green about code that is
not under review.

The positive, genuinely root-owned case is unit-level against the injected stat
seam (`protected-root-501.test.ts`), plus the CI job below.

## 7. Proposed CI job — real `sudo`, not mocked

Not added in this PR (the brief excluded it). This is the snippet to add when
someone owns the CI change; it is the only way to prove the ownership check
against a real root-owned file rather than a seam.

```yaml
# .github/workflows/policy-lock-sudo.yml
name: policy lock (real root-owned file)

on:
  pull_request:
    paths:
      - 'src/defence/iron-dome/protected-root.ts'
      - 'src/defence/iron-dome/policy-lock.ts'
      - 'src/cli/protect.ts'
      - 'src/cloud/config.ts'
      - 'scripts/pre-tool-hook.mjs'
      - 'plugins/openclaw/index.ts'
  push:
    branches: [main]

jobs:
  sudo-lock:
    # GitHub-hosted Ubuntu runners give the `runner` user passwordless sudo,
    # and the job runs UNPRIVILEGED — only the `protect` call is elevated. That
    # is the whole point: the reader must be a different uid from the writer.
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22.14'
          cache: npm
      - run: npm ci
      - run: npm run build:ts

      - name: Write a genuinely root-owned policy lock
        run: sudo node dist/index.js protect --from-config

      - name: The lock verifies for the unprivileged agent uid
        run: |
          set -eux
          test "$(id -u)" -ne 0            # the reader must not be root
          stat -c '%u %a' /etc/shieldcortex/policy.json | grep -qx '0 644'
          stat -c '%u %a' /etc/shieldcortex            | grep -qx '0 755'
          node dist/index.js config --policy-status | tee /tmp/status.txt
          grep -q 'policy locked by /etc/shieldcortex/policy.json' /tmp/status.txt
          grep -qv 'UNVERIFIABLE' /tmp/status.txt

      - name: A loosening write is refused
        run: |
          set -eu
          if node dist/index.js config --action-guard-disable; then
            echo "FAIL: the guard was disabled under a verified lock"; exit 1
          fi

      - name: Tightening still works
        run: node dist/index.js config --action-guard-enforce

      - name: doctor passes the lock row
        run: |
          node dist/index.js doctor --json > /tmp/doctor.json || true
          node -e '
            const r = JSON.parse(require("fs").readFileSync("/tmp/doctor.json","utf8").slice(
              require("fs").readFileSync("/tmp/doctor.json","utf8").indexOf("{")));
            const row = r.results.find((x) => x.label.includes("policy lock"));
            if (!row || row.status !== "pass") {
              console.error("policy lock row was", row); process.exit(1);
            }
          '

      - name: An agent-owned lock is refused even inside a root-owned directory
        run: |
          set -eux
          sudo rm -f /etc/shieldcortex/policy.json
          sudo install -o "$(id -u)" -g "$(id -g)" -m 644 /dev/null /etc/shieldcortex/policy.json
          echo '{"actionGuard":{"enabled":false}}' | sudo tee /etc/shieldcortex/policy.json > /dev/null
          sudo chown "$(id -u):$(id -g)" /etc/shieldcortex/policy.json
          node dist/index.js config --policy-status | grep -q 'UNVERIFIABLE'
```

Why each step is there rather than folded into one: the ownership assertions and
the refusal are different failures with different causes, and a single composite
step would report "the lock job failed" when what an operator needs to know is
*which* property stopped holding.

## 8. Alternatives considered

- **Move or rotate `.integrity-key`** — theatre; the same uid reads it.
- **Ed25519 signature with a pinned public key** — the pin has to live somewhere
  the agent cannot write, which is this same root-owned boundary with more moving
  parts. Worth it only for a remote authority (root-agent containers), later.
- **Privileged broker daemon** (separate uid, unix socket) — a superset of the
  lock; adds a process to keep alive and a fail-closed-when-socket-missing
  problem. The lock is the broker's static case; do it first.
- **OS keyring** — reachable by the same session; excluded by the threat model.

## 9. Deliberately not in this change

- `interceptor.enabled` and the plugin entry's own `enabled` flag are not in the
  protected set. Disarming the plugin wholesale is #500's boundary (hook wiring,
  expected hashes, install-root pin), which is expected to build on
  `resolveProtectedRoot` / `verifyProtectedFile` from this change.
- No migration: an existing install is simply unlocked until someone runs
  `protect`, and reports itself as such.
