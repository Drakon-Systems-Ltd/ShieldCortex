# #501 — OS-owned policy lock

*2026-09-16. Condensed from `shieldcortex-501-design-20260916.md`. Lands on
top of #500 (`1d57378d`, tool-call self-protection).*

## 1. What the config signature actually protects

Measured against `origin/main`, not remembered:

| Reader | Verifies `_sig`? | Effect of a same-UID edit |
|---|---|---|
| Claude Code hook (`loadActionGuardConfig`) | **No** — bare `JSON.parse`; also ignored `SHIELDCORTEX_CONFIG_DIR` | guard off, no forgery needed |
| OpenClaw plugin (`normaliseConfig` via the `openclaw.json` entry) | **No** — a different unsigned same-UID file | guard off, no forgery needed |
| `src/cloud/config.ts` `readRawConfigState` | Yes | `tampered` set `defenceMode: 'strict'` only; `actionGuard.enabled` was still read from the tampered bytes |
| doctor | Yes, indirectly | no tamper row existed |
| `hasTrustedMemorySidecarPosture` | Yes, strictly | the one place `_sig` gated a security decision — forgeable with the co-located key |

The conclusion that shaped everything below: the HMAC is a **corruption /
accidental-edit detector, not a tamper control**, and the two enforcement
surfaces never consulted it. Re-keying or relocating `.integrity-key` closes
nothing, because a same-UID process reads the key.

## 2. The shape

**Signing authority = the operating system's ownership boundary**, not a key the
agent can read.

- A human, once, as root, runs `shieldcortex protect`. It writes
  `/etc/shieldcortex/policy.json`, root-owned `0644`, in a root-owned `0755`
  directory. Agent-**readable** is fine and intended; agent-**writable** is the
  thing being removed. No cryptography: nothing to steal, no keyring, no second
  same-UID file.
- **Protected set v1** — `actionGuard.enabled`, `actionGuard.enforce`,
  `actionGuard.autoApprove` (ceiling), `actionGuard.broker.enabled`,
  `defenceMode` (floor), `memory.hostContract.posture`, `memory.inject.mode`.
- **Precedence** — for every covered key, take whichever of the lock and
  `config.json` is TIGHTER. That single rule is what "the lock wins; config may
  only tighten" means written as an operation rather than seven special cases.
  `autoApprove` is a ceiling (intersection); `defenceMode` is a floor (stricter
  rank); the two memory keys have no tightness order, so the lock is
  authoritative outright.
- **Verifier** — one function, one dist module: `lstat` says regular file and
  not a symlink, `uid !== euid`, no group/other write, and the same rules on
  every ancestor directory (unlink + create is governed by the DIRECTORY, not
  the file), then parses as JSON and matches the schema. Directories are checked
  with `stat` plus an `lstat` symlink-owner check, because `/etc` is a symlink on
  macOS and an lstat-only rule would refuse every Mac.

### Failing closed, precisely

- **Present but unverifiable** (wrong owner, writable dir, symlink, parse /
  schema fail, unknown version, dist verifier missing) → posture
  `{enabled: true, enforce: true, autoApprove: [], broker off, defenceMode: 'strict'}`,
  audit outcome `policy_unverifiable`, one stderr line. **Not** "deny every tool
  call": that bricks the agent and teaches operators to remove the lock.
- **Absent** → today's behaviour, plus a doctor row. FAIL when the guard is
  enabled (the operator believes tool calls are gated and a one-line edit says
  otherwise), WARN when it is off (nothing pinned to lose yet). Fix line is
  `protect`.
- **Agent running as root / Windows** → no lock is possible; doctor states it
  plainly. A remote policy authority is the later answer, not a fake local one.

### Schema versioning

Unknown KEYS are ignored, so a newer `protect` cannot push older installs on a
fleet into fail-closed. An unknown VERSION is a failure, because a v2 policy may
mean something a v1 reader would get quietly wrong.

## 3. Legacy local key — explicit compatibility

`.integrity-key`, embedded `_sig`, legacy `.config-sig` and the `self-heal`
verdict are **unchanged, not relocated, not migrated**. They keep their real job
(torn write / accidental edit) and the docs stop calling it tamper protection.

Two semantic fixes inside the existing scheme:

1. A `tampered` verdict now forces the whole fail-closed posture from §2, from
   the same constant. Previously it set `defenceMode` and nothing else, so the
   guard's own switches were read straight out of the bytes the integrity check
   had just called untrustworthy.
2. `hasTrustedMemorySidecarPosture` requires the lock to declare the posture when
   a lock exists, and falls back to `_sig` only when unlocked. A locked host
   whose lock is silent on the memory keys answers `false`: silence from the
   authority is not permission.

## 4. Both enforcement surfaces

One implementation of the precedence rules, in
`src/defence/iron-dome/policy-lock.ts`, imported from `dist` by both surfaces —
the hook through its existing lazy-dist pattern, the plugin through
`shieldcortex/defence`.

Behind each sits a small **inline existence probe** that imports nothing. A
missing dist normally degrades to the inline catastrophic fallback, because
turning every tool call into a denial whenever a build is stale is the outage
ShieldCortex exists to prevent — but on a host with a lock file that would make
"delete dist" the bypass. So a present lock plus an unavailable reader forces the
strict posture. Only the fail-closed literal is duplicated; the parity suite
asserts the two copies still match `STRICT_FAILCLOSED_POSTURE`.

Ordering matters on the plugin: the `openclaw.json` entry deep-merges OVER the
shield config, so the lock is applied AFTER `mergeConfigs`. Applied earlier, an
unsigned same-UID `enabled: false` would still have the last word — the exact
bypass being closed. `openclaw-plugin-guard-sync` writes into that same entry, so
it is out-ranked on read and refused on write.

The hook also now honours `SHIELDCORTEX_CONFIG_DIR`. It hard-coded
`~/.shieldcortex`, so on any box using the override it was enforcing against a
different config from the rest of the product.

## 5. The `SHIELDCORTEX_PROTECTED_ROOT` test seam

The design rule is "override only via a root-owned file, never env", and the
production override honours it: `/etc/shieldcortex.conf`, a root-owned pointer
file that must itself pass `verifyProtectedFile`.

`SHIELDCORTEX_PROTECTED_ROOT` is a separate, deliberately **non-loosening** test
seam. BOTH production rules are resolved FIRST — the canonical root and the
root-owned pointer — and if either answers, the variable is ignored outright. An
agent that sets it therefore cannot hide a real lock; on a host with no lock the
only thing it can do is introduce one, and a lock the agent can write is by
definition same-UID, hence unverifiable, hence STRICTER than unlocked. It exists
because the regression proof has to drive the built dist and the built hook as
separate processes and may not write to `/etc`.

The pointer half of that ordering is a correction, not an original claim. As
first built, the env branch was gated on the **canonical** root alone and the
pointer was evaluated after it — which is sound only on a host that uses
`/etc/shieldcortex`. A pointer host by definition keeps policy somewhere else,
so `/etc/shieldcortex` does not exist there, and one variable walked the
resolver away from a genuinely root-owned, verified pointer root: `locked` →
`absent`, straight to unlocked. The adversarial review found it (BLOCK-2) and
`protected-root-501` now pins the case: a verified pointer plus a hostile env
value must still resolve to the pointer's locked state. Both inline probes
(`scripts/pre-tool-hook.mjs`, `plugins/openclaw/index.ts`) mirror the corrected
ordering, which also closes the second half of the same defect — on a pointer
host with a broken build, the probes used to answer `false` and both surfaces
failed **open**.

### The sibling seam: `SHIELDCORTEX_DIST_ROOT`

`scripts/pre-tool-hook.mjs` carries a second, older seam — the variable that
says where `dist` is. It pre-dates #501 and is not part of the lock's design,
but it is the lock's problem, because the hook resolves *every* enforcement
module through it: the lock reader, and the classifier that returns the
allow/deny verdict.

Gating only the reader is not enough, and the review proved it twice. Point the
variable at a `policy-lock.js` answering `absent` and the lock evaporates
(BLOCK-1). Point it instead at a `tool-action-guard.js` whose `evaluateToolCall`
returns `allow` and the outcome is strictly *worse* (NEW-1): the lock is read
correctly, the strict posture is computed, the operator is even told on stderr —
and the posture is then handed to the attacker's classifier, which permits
everything. One file, in a directory the agent already owns, with a lock on disk.

So the gate is not per-module. `hookDistRoot()` is the one place the file
decides where `dist` is, every loader resolves through it, and on a host where
the inline probe can see a lock the variable is ignored outright — a loader
added later inherits that instead of needing its own carve-out. Conditioned on
the lock, not on the variable: on an unlocked host it still resolves exactly
where it is pointed, because there it buys an attacker nothing, and that is
every developer and every suite that uses the seam.

It closes the *environment* route only. A `dist` whose contents an attacker
chose is install tampering — §8.6, and #500's boundary.

## 6. Regression proof

`src/__tests__/policy-lock-dist-regression-501.test.ts` drives the BUILT
artefacts. Fixture: hermetic `HOME` + `SHIELDCORTEX_CONFIG_DIR`, a
`.integrity-key` and a `config.json` carrying a genuinely valid embedded `_sig`
computed with it (the SC-02 forge), `actionGuard.enabled: false` inside those
correctly-signed bytes, and a same-UID `policy.json`. The first assertion is that
the integrity check ACCEPTS the forgery — otherwise the suite would be proving
something weaker than it claims.

Then: `dist/index.js doctor --json` reports the lock invalid and the posture
enforced; the built `scripts/pre-tool-hook.mjs` DENIES the SC-01 catastrophic
payload; `config --action-guard-disable` is refused by name; `config
--cloud-status` prints the enforced posture (the assertion that travels through
`readRawConfigState`'s precedence rather than a surface that reads the lock
directly). The suite rebuilds on a STALE dist, not just a missing one: a build
left over from before the fix exists, and would report green about code that is
not under review.

`src/__tests__/policy-lock-chain-e2e-501.test.ts` closes the remaining gap in
that proof: the third enforcement surface. The OpenClaw plugin is a SEPARATE
tsc project (`plugins/openclaw/dist/`) that reaches the precedence rules through
a bare `import('shieldcortex/defence')` — a specifier that only resolves on a
real install layout — so a plugin which compiled but could no longer resolve it
would keep every unit test green while enforcing nothing. The suite therefore
stages an install the way a host has one (`<stage>/node_modules/shieldcortex`
symlinked at the package, `<stage>/plugin` a copy of the built plugin dist) and
drives it from a child process against the same forge. It states the chain claim
as an equality rather than three separate greens: one lock on disk, read by the
hook, the CLI and the plugin — three programs, two build outputs, no shared
process state — must produce one posture, in one test. It also pins the
plugin-specific ordering (the lock applied AFTER `mergeConfigs`, so the
`openclaw.json` entry cannot have the last word) and the plugin's inline probe
(an unresolvable defence module plus a lock forces the strict posture; the same
broken install with no lock stays silent).

Both suites rebuild a STALE build, and `build:ts` begins by deleting both dist
trees, so they share a `mkdir`-based cross-process lock
(`src/__tests__/built-artefact-freshness.ts`) — otherwise two Jest workers each
deciding to rebuild would leave one driving a dist the other just removed.

The positive, genuinely root-owned case is unit-level against the injected stat
seam (`protected-root-501.test.ts`), plus the CI job below.

## 7. Proposed CI job — real `sudo`, not mocked

Not added in this PR (the brief excluded it). This is the snippet to add when
someone owns the CI change; it is the only way to prove the ownership check
against a real root-owned file rather than a seam.

```yaml
# .github/workflows/policy-lock-sudo.yml
name: policy lock (real root-owned file)

on:
  pull_request:
    paths:
      - 'src/defence/iron-dome/protected-root.ts'
      - 'src/defence/iron-dome/policy-lock.ts'
      - 'src/cli/protect.ts'
      - 'src/cloud/config.ts'
      - 'scripts/pre-tool-hook.mjs'
      - 'plugins/openclaw/index.ts'
  push:
    branches: [main]

jobs:
  sudo-lock:
    # GitHub-hosted Ubuntu runners give the `runner` user passwordless sudo,
    # and the job runs UNPRIVILEGED — only the `protect` call is elevated. That
    # is the whole point: the reader must be a different uid from the writer.
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22.14'
          cache: npm
      - run: npm ci
      - run: npm run build:ts

      - name: Write a genuinely root-owned policy lock
        run: sudo node dist/index.js protect --from-config

      - name: The lock verifies for the unprivileged agent uid
        run: |
          set -eux
          test "$(id -u)" -ne 0            # the reader must not be root
          stat -c '%u %a' /etc/shieldcortex/policy.json | grep -qx '0 644'
          stat -c '%u %a' /etc/shieldcortex            | grep -qx '0 755'
          node dist/index.js config --policy-status | tee /tmp/status.txt
          grep -q 'policy locked by /etc/shieldcortex/policy.json' /tmp/status.txt
          grep -qv 'UNVERIFIABLE' /tmp/status.txt

      - name: A loosening write is refused
        run: |
          set -eu
          if node dist/index.js config --action-guard-disable; then
            echo "FAIL: the guard was disabled under a verified lock"; exit 1
          fi

      - name: Tightening still works
        run: node dist/index.js config --action-guard-enforce

      - name: doctor passes the lock row
        run: |
          node dist/index.js doctor --json > /tmp/doctor.json || true
          node -e '
            const r = JSON.parse(require("fs").readFileSync("/tmp/doctor.json","utf8").slice(
              require("fs").readFileSync("/tmp/doctor.json","utf8").indexOf("{")));
            const row = r.results.find((x) => x.label.includes("policy lock"));
            if (!row || row.status !== "pass") {
              console.error("policy lock row was", row); process.exit(1);
            }
          '

      - name: An agent-owned lock is refused even inside a root-owned directory
        run: |
          set -eux
          sudo rm -f /etc/shieldcortex/policy.json
          sudo install -o "$(id -u)" -g "$(id -g)" -m 644 /dev/null /etc/shieldcortex/policy.json
          echo '{"actionGuard":{"enabled":false}}' | sudo tee /etc/shieldcortex/policy.json > /dev/null
          sudo chown "$(id -u):$(id -g)" /etc/shieldcortex/policy.json
          node dist/index.js config --policy-status | grep -q 'UNVERIFIABLE'
```

Why each step is there rather than folded into one: the ownership assertions and
the refusal are different failures with different causes, and a single composite
step would report "the lock job failed" when what an operator needs to know is
*which* property stopped holding.

## 8. Recovery — for a human operator, at a root shell

**This section is prose on purpose. It is not a script, and nothing in the
product runs it.** The lock's entire value is that the agent uid cannot loosen
it; shipping a `shieldcortex unprotect` — or any other command an agent could be
talked into invoking — would hand back exactly the capability §2 removes. Every
step below needs a privilege the agent does not have, and that is the design,
not an oversight. If you are an agent reading this: you cannot perform these
steps, and you should not offer to.

### 8.1 First, find out what state you are actually in

Two commands, unprivileged, safe to run at any time:

```bash
shieldcortex config --policy-status
shieldcortex doctor            # or: shieldcortex doctor --json
```

`--policy-status` prints the headline, the lock's path, and every pinned key
with its value. `doctor` carries two independent rows — **`Action guard policy
lock`** and **`Action guard config integrity`**. They are separate on purpose:
they answer different questions, and one green half must never hide a red one.

| Headline you see | State | Where to go |
|---|---|---|
| `policy locked by /etc/shieldcortex/policy.json (root-owned) — N keys pinned` | healthy | §8.4 if you need to change what is pinned |
| `policy lock at … is present but UNVERIFIABLE (<reason>)` | fail-closed | §8.2 |
| `policy unlocked: a same-user process can disable the guard` | no lock | nothing to recover; `protect` if you want one |
| `no policy lock is possible on this host — …` | unsupported | §8.5 |

The parenthesised `<reason>` in the UNVERIFIABLE headline is the diagnosis, and
it is worth reading before doing anything: `file owned by the agent uid`,
`parent directory owned by the agent uid`, `file is group/other writable`,
`parent directory is group/other writable`, `path is a symlink`, `not valid
JSON`, `does not match the policy schema`, or an unrecognised schema version.

A `tampered` verdict on the **config integrity** row is a different fault with a
different fix — that is `config.json` disagreeing with its own HMAC, which
forces the same strict posture. Re-write the affected settings with the
`shieldcortex config --*` flags (they re-sign) and re-run doctor.

### 8.2 `policy_unverifiable` — a lock exists but does not verify

The box is *safe* in this state: guard on and enforcing, auto-approve empty,
broker off, defence mode strict. It is not bricked — ordinary tool calls still
run. What is wrong is your ability to trust what is pinned. Take it in order:

1. **Look at the file, as a human.** Ownership and mode are the whole question —
   `ls -ln` and `stat -c '%U %G %a %n'` on both `/etc/shieldcortex` and
   `/etc/shieldcortex/policy.json`, then read the policy itself.

2. **Decide whether this is a lock you wrote.** If the reason is `file owned by
   the agent uid` and you never ran `protect` on this host, you are not looking
   at a damaged lock — you are looking at a file something running as the agent
   put there. Treat that as an incident before you treat it as a repair: check
   `shieldcortex audit` for `policy_unverifiable` entries and note the file's
   mtime. Rewriting it first destroys the evidence.

3. **Repair, as root.** For a wrong owner or a loose mode, the correct fix is to
   let `protect` rewrite the artefact rather than to hand-patch it — it writes
   atomically, sets `0644` in a `0755` root-owned directory, and then re-verifies
   the result *as the agent uid would see it*, reporting failure loudly instead
   of claiming success:

   ```bash
   sudo shieldcortex protect --dry-run       # read this before the next line
   sudo shieldcortex protect
   ```

   `protect` reads *your* config, not root's: it honours `--config <path>`, then
   `SHIELDCORTEX_CONFIG_DIR`, then `$SUDO_USER`'s home.

4. **If you would rather run unlocked**, delete `/etc/shieldcortex/policy.json`
   as root and say so out loud in your change log — the host goes back to "any
   same-user process can disable the guard", which doctor then reports as a FAIL
   for as long as the guard is on.

### 8.3 A corrupted or unparseable lock

Same posture, same commands as §8.2 — `not valid JSON` and `does not match the
policy schema` are ordinary damage (a truncated write, a hand edit, a
half-finished config-management run). `sudo shieldcortex protect --dry-run` shows
the replacement first; `sudo shieldcortex protect` installs it atomically, so a
failed write leaves the previous lock intact rather than a half-written one.

An **unrecognised schema version** is the one case where rewriting may be the
wrong move: it means the file was written by a *newer* ShieldCortex than the one
reading it. Upgrade the reader before you overwrite a policy you may not fully
understand.

### 8.4 You are locked out of loosening a setting you need to change

This is the feature behaving correctly, so there is no clever local answer — but
there is a straightforward one, and it takes root, once:

1. Confirm what is actually pinned: `shieldcortex config --policy-status`.
2. Edit the source config to the policy you now want.
3. Re-pin it as root:

   ```bash
   sudo shieldcortex protect --from-config --dry-run
   sudo shieldcortex protect --from-config
   ```

   `--from-config` pins the config verbatim, including an Action Guard that is
   OFF. Without it, `protect` forces `enabled: true, enforce: true` regardless —
   a command called `protect` that silently froze the guard off because that was
   today's setting would be a trap.
4. **Re-sign `config.json` by re-running the setting through the CLI**, e.g.
   `shieldcortex config --action-guard-advisory` for the change you hand-edited
   in step 2. This step is not optional and it is not cosmetic.

   Step 2 hand-edits `config.json`, which invalidates its `_sig`. Since #501 a
   `tampered` verdict forces the **whole** fail-closed posture (§3,
   `src/cloud/config.ts`), unconditionally and *independently of the lock* — so
   a hand-edited config sits in strict no matter how loose the lock you just
   pinned is. And `applyPolicyLock` only ever tightens, so re-pinning a looser
   lock cannot pull it back down. Steps 1-3 alone therefore leave you exactly
   where you started, with no visible reason why; the adversarial review
   reproduced it (SHOULD-FIX-5) before this step existed.

   The re-run is *permitted* now, and was not before: the write that
   `refuseIfPolicyLockForbids` was refusing is the one the new, looser lock
   allows. Confirm with `shieldcortex config --cloud-status` — the posture it
   prints is the posture the box is in. If it still says `strict`, the config is
   still unsigned; `shieldcortex doctor`'s config-integrity row will say so.
5. Or remove the lock entirely (§8.2 step 4) and re-pin later.

Note what you do *not* need to do: you can always make a locked host **stricter**
without touching the lock at all. Precedence takes the tighter of lock and
config per key, so `shieldcortex config --action-guard-enforce` on a locked box
succeeds normally. Only a loosening write is refused, and the refusal names the
key and the file that is refusing.

**If you no longer have root on this host**, the lock is doing precisely what it
was installed to do and there is no in-product recovery. Recover root the way
you would for any other root-owned file — console or hypervisor access, the
cloud provider's rescue path, or re-provisioning. Do not ask the agent to help;
if it could, the control would not exist.

### 8.5 `unsupported` — no boundary to recover

Reported on Windows, and on a host where the agent itself runs as root. Nothing
is broken and nothing local will fix it: with the agent already privileged there
is no ownership boundary between the writer and the reader. Run the agent as an
unprivileged user, or wait for the remote policy authority (§9). A fake local
lock would be worse than none.

### 8.6 What NOT to do

- **Do not delete `~/.shieldcortex` and expect a clean slate.** The lock is not
  in there — it is in `/etc/shieldcortex`, which is the point — so it survives,
  and a host whose config is missing or `tampered` sits in the strict
  fail-closed posture, which is a *stricter* state than the one you were trying
  to leave. Removing the config does not remove the lock, and cannot.
- **Do not re-own or loosen the mode of the lock to "make it work".** Handing
  the file to the agent user converts the fault from "damaged" to
  `owned-by-agent`, which is permanently unverifiable, which is permanently
  strict. It is the one edit guaranteed to make the state worse.
- **Do not set `SHIELDCORTEX_PROTECTED_ROOT` to point somewhere else.** It is a
  non-loosening test seam (§5): both production rules — the canonical root and
  the root-owned pointer file — are resolved first, and the variable is ignored
  outright if either answers, so it cannot hide a real lock. On an unlocked host
  the only thing it can do is *introduce* one.
- **Do not hand these steps to an agent to execute**, and do not wrap them in a
  script the agent can call. An automated `unprotect` is a bypass with better
  ergonomics; a human at a root shell is the control.
- **Do not reach for a downgrade.** A lock present with an unreadable policy
  reader is exactly the case both enforcement surfaces fail closed on — their
  inline probes see the file without resolving anything from `dist`. (Replacing
  the whole install with a pre-#501 build does remove the reader; controlling
  what is installed is a different boundary, and #500's.)
- **Do not treat an UNVERIFIABLE lock you did not write as a config problem.**
  See §8.2 step 2. It is the signature of something running as the agent having
  written a file in a place it should not have been able to.

## 9. Alternatives considered

- **Move or rotate `.integrity-key`** — theatre; the same uid reads it.
- **Ed25519 signature with a pinned public key** — the pin has to live somewhere
  the agent cannot write, which is this same root-owned boundary with more moving
  parts. Worth it only for a remote authority (root-agent containers), later.
- **Privileged broker daemon** (separate uid, unix socket) — a superset of the
  lock; adds a process to keep alive and a fail-closed-when-socket-missing
  problem. The lock is the broker's static case; do it first.
- **OS keyring** — reachable by the same session; excluded by the threat model.

## 10. Deliberately not in this change

- `interceptor.enabled` and the plugin entry's own `enabled` flag are not in the
  protected set. Disarming the plugin wholesale is #500's boundary (hook wiring,
  expected hashes, install-root pin), which is expected to build on
  `resolveProtectedRoot` / `verifyProtectedFile` from this change.
- No migration: an existing install is simply unlocked until someone runs
  `protect`, and reports itself as such.
