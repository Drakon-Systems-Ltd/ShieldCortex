# Conversation UUID false-taint correction (#911)

A bare UUID is not evidence of a Heroku credential. The Heroku rule now requires a same-line Heroku identifier within 64 characters before the UUID. Explicit HEROKU_API_KEY assignments and nearby provider context remain detected; other provider detectors are unchanged.

The context is a lookbehind, so the Heroku match, its reported position and its redaction range are the UUID alone. It therefore cannot hide a stronger rule that matches the same text: `HEROKU_API_KEY=<uuid>` and `heroku token: <uuid>` still produce the high-severity, blocked assignment finding they produced before this change (plus the low-severity Heroku finding), and an unrelated secret between the provider word and the UUID (`heroku password=<value> <uuid>`) keeps its own finding. More generally, the direct pattern pass now skips a match contained in an earlier range only when that range is of equal or higher severity. Each UUID on the line is checked against its own context, so `heroku tokens: <uuid>, <uuid>` reports and redacts both.

The separator-collapsed pass (#543) does not run the Heroku rule: collapsing removes the line breaks and spacing the context bound is measured over, so `heroku:` followed by a newline, or by 100 spaces, before a UUID would otherwise borrow context the original text does not have. Split UUIDs were already treated as public identifiers by that pass, so no split-key detection is lost.

Credential-only tool-response summaries remain threats for reporting and credential redaction, but do not establish instruction steering and therefore do not raise conversation session taint. Any additional instruction, injection, encoding, exfiltration or other threat layer retains the prior taint policy. This applies to credential-only findings at all confidence levels, not just low-confidence UUID matches.

The OpenClaw llm_input prompt is an unsegmented string and can include host framing and quoted conversation history. The supported event contract supplies no attested per-span origin. It is therefore labelled unknown rather than user. Structured user text blocks remain user; structured tool output remains tool_result. Neither textual OpenClaw markers nor XML-like wrappers establish host trust. Unknown content remains scanned; this change does not exempt host-looking strings or invent a trusted host label.

The internal-content exemption (boot checks, heartbeats) no longer applies to the prompt on text alone. Before this change, any prompt opening with `Read HEARTBEAT.md`, `System:` or a similar marker skipped scanning on every session, including a direct message, so an injection placed after such a prefix was never scanned. The prompt is now exempt only when the host-minted session key identifies an isolated cron or heartbeat run (#353) and the prompt, after at most one host cron envelope, is internal content. The session key is a structured event field, not prompt text. History messages never receive this automation exemption. On an ordinary session an unwrapped heartbeat ritual is scanned; the genuine ritual scans clean and does not taint.

Limitation: genuine host framing that matches an instruction detector can still be detected and taint. Safely exempting such spans requires structural origin metadata from the host, not content matching. This patch does not change live posture, approval handling, owner trust, or the host event contract.
