# Competitive Teardown: destructive_command_guard (dcg) vs ShieldCortex Action Guard

**Date:** 2026-07-12 · **Scope:** read-only analysis, input to 4.47.4 planning · **Sources:** `/tmp/dcg-teardown` (dcg, cloned read-only), `~/clawd/projects/ShieldCortex` source

## Executive Summary

dcg is a mature, single-purpose Rust CLI (848 destructive patterns across 25+ product packs) with a formal 3-tier detection pipeline (keyword prefilter → heredoc/inline trigger regex → AST scan) and a structural confidence-scoring model that classifies *where* a match sits (executed/data/comment/argument span) before deciding block vs warn. ShieldCortex's Action Guard covers a comparable set of *generic* danger categories (~25) but is missing product-specific coverage (no kubectl/terraform/vault/stripe-style verbs) and, more importantly, fixes false positives with one bespoke carve-out per bug number (#71/#72/#73) rather than a generalizable span/confidence model — the exact failure mode dcg's `context.rs` was built to solve structurally. SC's realtime in-process interceptor and fail-closed canary are architecturally sound and arguably ahead of dcg's static/CLI model on integration depth. Biggest wins available: adopt dcg's span-classification approach to replace patch-by-patch FP fixing, and add a structured, audited temporary-exception mechanism in place of purely ephemeral interactive approval.

## Top 5 Recommended Ports (ranked by value/effort)

1. **Span-classification confidence model to replace ad hoc FP patches** — Value: High / Effort: Medium. Port dcg's `context.rs` idea (classify each regex match's span as Executed / Argument / Comment / Data / Heredoc-body, weight by execution-operator proximity, threshold to decide block vs warn) as a shared utility Action Guard and the firewall detectors both call. This directly replaces the #71/#72/#73 pattern of "one bespoke isPurePrint/stripComments/outbound-verb fix per bug" with one mechanism that generalizes to the *next* false-positive shape, which is exactly the recurring cost center flagged in project memory. Does not require ast-grep/AST parsing — a tokenizer-level span classifier gets most of the value.

2. **Structured, audited, expiring temporary-exception ("allow-once") mechanism** — Value: Medium-High / Effort: Low-Medium. SC currently has only ephemeral interactive approve/deny (not persisted) or permanent `autoApprove` config edits (manual, no expiry). Port dcg's model minus its rigid 24h/short-code specifics: an exception scoped to exact command + path/session, with a defined TTL, single-use option, and its own audit log line distinct from the general decision log — reduces friction for legitimate one-off dangerous actions without permanently loosening config. Do not copy the fixed 24h TTL verbatim; make it configurable and keep it structurally incapable of touching the catastrophic tier, preserving SC's "cannot fail open on catastrophic" guarantee.

3. **Static safer-alternative suggestions attached to each catastrophic/dangerous rule** — Value: Medium / Effort: Low. Cheap, high-visibility UX win: attach a one-line `SaferAlternative`/`PreviewFirst` string to each rule (e.g., `git reset --hard` → "run `git diff` first, or use `git reset --soft`"; `docker system prune -f` → "run without `-f` to preview first"). Pure static string tables, no new detection logic — lowest-effort item on this list.

4. **Targeted pack expansion for tools actually in Michael's stack** — Value: Medium-High / Effort: Medium. Not a full port of dcg's 40 packs (most are irrelevant here) — specifically add: `op item delete`/`op vault delete` (1Password, heavily used), `git reset --hard`/`git clean -f`/`git stash drop`/`git branch -D` as their own dangerous-tier rules (currently bucketed under generic sensitive `git-mutate`), and basic `docker system prune`/`volume rm`/`rmi -f` coverage. Skip database/cloud/k8s/IaC packs until those tools actually appear in this environment — adding them now is speculative coverage for zero observed usage.

5. **Auto-mined allowlist suggestions from the existing audit log** — Value: Medium / Effort: Medium-High. SC already writes every decision to `~/.shieldcortex/audit/*.jsonl`; a periodic job could cluster repeated denials/approvals (dcg's Jaccard-similarity approach) and propose `autoApprove` config additions instead of requiring Michael/Jarvis to hand-edit config after every recurring false positive. Ranked last because it depends on item 1 landing first (span classification reduces noise the clustering would otherwise have to filter) and is the most speculative/exploratory of the five.

## Do NOT Port

- **Full ast-grep/AST-based structural matching engine** — SC's field-discipline design (only scanning extracted `command`/`path`/`url`, never free-text agent output) already sidesteps most of what dcg's AST layer defends against; bolting a Rust-grade AST parser onto a Node-embedded realtime guard is disproportionate engineering cost relative to the marginal detection gain over item #1 above.
- **regex-automata DFA backend** — dcg's own ADR (docs/decision-dfa-backend.md) concluded this was 2–6% *slower* with no meaningful ReDoS benefit at their pattern-set size; irrelevant to port, and SC's pattern set is smaller still.
- **3-tier Aho-Corasick keyword-prefilter architecture** — solves a scale problem (848 patterns, sub-10µs budget) that SC does not have at ~25 rule categories; premature optimization until/unless item #4 above grows the rule count materially.
- **Long-tail SaaS/infra packs** (payment providers, messaging brokers, monitoring/observability, feature-flag platforms, CDNs, search engines, API gateways, CI/CD platforms beyond basic git) — none of these products are used in this environment; porting would bloat the rule surface for zero real coverage and increase FP risk for no benefit.
- **Windows/PowerShell pack** — ShieldCortex's actual deployment targets here are Linux and macOS hosts; no Windows agent surface exists to protect.
- **Fixed 24-hour allow-once TTL semantics verbatim** — the *concept* (item #2) is worth porting, but copying dcg's specific non-configurable 24h expiry risks accidentally creating a longer-lived bypass window than SC's current stricter, session-scoped approval model — keep the port more conservative than the source.
