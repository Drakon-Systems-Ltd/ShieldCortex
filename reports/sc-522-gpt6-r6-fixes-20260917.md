## Deviations from the spec, and why

1. **`defenceMode` is pinned at `balanced`, not omitted.** The spec said leave
   `policy.defenceMode` unset. The prior lane pinned the product default
   instead, and after checking `policy-lock.ts:594-596` I kept that: the lock
   applies `defenceMode` as a **floor** (effective = stricter of locked and
   configured rank). Pinning `balanced` lets config raise to `strict` and blocks
   a drop to `permissive`; omitting the key leaves `permissive` reachable. The
   spec's version is the weaker of the two. `DEFAULT_DEFENCE_MODE` is now
   exported from `policy-lock.ts` so the floor and the product default cannot
   drift. This is a behaviour change for an operator who deliberately runs
   `permissive` and then runs a flag-less `protect` — documented in the
   CHANGELOG and the design doc; `--from-config` still pins `permissive`
   verbatim. **Flagging it for Michael/GPT-6/Grok as the one judgment call in
   this batch.**
2. **`protect` without `--from-config` reads no config at all**, rather than
   reading it and discarding four keys. Strictly stronger than asked; it means
   no same-UID bytes are parsed on that path at all.
3. **The #3 fix is one gate, not four.** The spec asked for four independent
   gates. The implementation is a single early return
   (`if (!opts.fromConfig) return safeDefaultPolicy();`), which is cleaner. To
   still get per-key evidence I ran five fine-grained reverts that leak exactly
   one key back through the default path — see below.
4. **The "root-owned ancestor, unprivileged agent uid" positive fixture** the
   spec worried might be inexpressible without real root **is** expressible:
   the prior lane covered it against an injected `ProtectedFsSeam`. Both the
   already-exists and missing-root positive paths are asserted.
